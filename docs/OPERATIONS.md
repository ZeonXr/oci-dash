# 运维说明

本指南适用于单主机 Docker Compose 部署。服务为 `app`，仓库默认镜像为 `ghcr.io/zeonxr/oci-dash:latest`，默认挂载为 `./data:/data`；宿主数据目录位于 `compose.yaml` 旁，容器内数据库为 `/data/oci-dash.db`。源码开发和本地镜像构建见[贡献指南](../CONTRIBUTING.md)。

## 默认部署

默认只需 Docker Engine、Docker Compose 和仓库的 [compose.yaml](https://raw.githubusercontent.com/ZeonXr/oci-dash/main/compose.yaml)，无需源码、Node.js、`.env` 或其他仓库文件。它直接引用 `latest` 镜像，不包含 `build` 或 `extends`；需要固定版本时，可改用对应 GitHub Release 的 Compose 附件。

在独立部署目录，用浏览器下载并保存为 `compose.yaml`，或执行：

```sh
curl -fL https://raw.githubusercontent.com/ZeonXr/oci-dash/main/compose.yaml -o compose.yaml
```

在该目录直接启动，Docker 会创建缺失的 `data` 目录：

```sh
docker compose up -d --wait
```

本版使用 Drizzle 初始数据库结构，首次部署需使用独立的空 `data` 目录。应用不转换接入 Drizzle 之前的数据库；已有其他版本的数据应保留在原目录，并使用与其匹配的镜像，不要把新部署直接指向该目录。

容器默认以 root 运行，无需预先设置 UID/GID 或执行 `chown`。Docker Desktop 需允许 Docker 访问部署目录。

发布目标平台为原生 Linux `amd64`、`arm64`，由 Docker 按主机架构选择镜像。镜像索引、匿名拉取及发布资产的验证状态见[发布验收](VERIFICATION.md#v058-发布验收)。重启策略、35 秒停止期限和 `local` 日志驱动直接保留在这份 Compose 中。

打开 `http://localhost:6240`，填写管理员用户名、密码和确认密码。页面也能生成并复制 32 位随机密码；创建成功后自动登录并关闭初始化入口。第一次能访问该页面的人可以成为管理员，因此应先通过本机或[SSH 隧道](#https-与访问)完成，再开放公共反向代理。无须读取初始密码文件、配置额外令牌或填写环境变量。

首次启动自动生成加密密钥，后续启动复用已保存的数据：

- 默认空数据库等待网页设置管理员；已有管理员继续使用原用户名和密码，重启或升级不会重置。
- OCI 凭据和 MFA 的加密密钥位于 `/data/.master-key`。不能删除或替换它；数据库会校验配对关系，缺失或不匹配时拒绝启动。
- 数据库位于 `/data/oci-dash.db`；完整备份宿主 `./data` 即可包含数据库和密钥，不能遗漏隐藏文件和配套 WAL。
- Docker 使用 `local` 日志驱动自动轮转，默认保留最多 5 个、每个 20 MB 的日志文件，并压缩已轮转的日志。

主密钥及数据库文件在 Linux 上使用 `0600` 权限，新建文件通常由 root 所有；在宿主机手工管理或恢复这些文件时使用相应权限。应用不会递归修改已有数据的属主或替换主密钥。

## 可选配置

部署配置直接写在 Compose 中，无需 `.env`。默认端口映射为 `127.0.0.1:6240:3000`，只绑定 loopback；自定义宿主端口时修改中间的 `6240`，容器内保留 `3000`，同步修改反向代理与 SSH 隧道，然后执行 `docker compose up -d --wait app`。

默认数据挂载为 `./data:/data`。相对路径依据 `compose.yaml` 所在目录解析，不是临时执行命令的目录；生产部署目录应与源码和构建目录分开。更换本版数据的保存位置时，先停机备份完整目录，再修改挂载来源；使用绝对路径更容易核对。

### 更换数据位置

修改 Compose 的挂载来源只切换位置，不会搬迁数据。切到空目录后出现初始化页面或空面板，不代表原账号被删除。

1. 等待任务和控制台结束，在旧配置下执行 `docker compose stop app`，确认应用停止；记录旧挂载和项目名。
2. 按[备份流程](#备份)保存整个旧 `/data`。备份脚本会保持原本已停止的应用为停止状态。
3. 准备一个独立、空的新目录，将本版数据全量复制或解压进去，保留文件所有者及权限。包括隐藏的 `.master-key`、数据库和配套 WAL/SHM 文件，不能只复制 `.db`。可使用完整备份归档恢复，或在 Linux 上使用保留属性的复制，例如 `cp -a /源目录/. /目标目录/`。
4. 确认新挂载可读写，且内容与停止后的旧数据一致，再修改 Compose 的挂载来源。Windows 通过宿主 ACL 核对访问。保留原目录或命名卷及备份。
5. 执行 `docker compose up -d --force-recreate --wait app`，确认原管理员、账号和资源均在，再恢复使用。若显示空面板，先停止应用并核对挂载，不要重新导入账号。

使用新的命名卷时同样需要先完整恢复本版数据，并在 Compose 中声明该卷。更换保存位置不改变数据库结构，也不需要修改容器内的 `DATABASE_PATH`。

### 高级应用变量

以下应用变量仅供高级部署或本地开发使用；Docker 中需显式加入 `compose.override.yaml` 的 `services.app.environment`。不要用 `env_file: .env` 把本地数据库路径或宿主机端口一起注入容器。

| 变量                      | 含义                                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------- |
| `ADMIN_USERNAME`          | 仅配合显式 `ADMIN_PASSWORD` 指定首次管理员名称，默认 `admin`；网页初始化时由用户填写。   |
| `ADMIN_PASSWORD`          | 显式指定 12–256 字符密码时初始化空数据库并跳过网页设置；默认留空，已有管理员不覆盖。     |
| `MASTER_KEY`              | 可选的 Base64 编码 32 字节密钥；验证成功后也持久化到 `.master-key`，必须与已有数据匹配。 |
| `APP_ORIGIN`              | 可选固定访问源，如 `https://oci.example.com`；默认按请求的 Host 和 Origin 校验。         |
| `PORT`                    | 容器应用监听端口，默认 3000；默认 Compose 不注入该变量。日常只修改宿主端口映射。         |
| `DATABASE_PATH`           | 本地默认 `data/oci-dash.db`；Compose 固定为 `/data/oci-dash.db`。                        |
| `NEXT_TELEMETRY_DISABLED` | 镜像已设置为 `1`，关闭 Next.js 遥测。                                                    |

例如只允许从一个固定域名登录，可使用以下可选覆盖文件，通常不需要配置：

```yaml
services:
  app:
    environment:
      APP_ORIGIN: https://oci.example.com
```

开发及工具脚本要求 Node.js `>=26.13 <27`，与镜像一致的版本为 `26.13.0`；仅部署容器无需安装宿主机 Node.js。首次部署见 [README](../README.md#docker-部署)。修改容器配置后需要重新创建：

```sh
docker compose up -d --force-recreate app
```

Web、网关和 Worker 使用同一数据库和密钥文件。本地运行默认将这些文件保存在 `data/`。

新数据库完成网页初始化后是普通空面板，不生成默认账号、示例资源或初始密码文件。暂停执行任务或控制台恢复时应停止应用进程。

## HTTPS 与访问

Compose 默认仅发布 `127.0.0.1:6240`。反向代理应将 HTTPS 域名转发到该地址；修改了宿主端口映射时使用对应端口。代理若在另一个容器中，不能把自己的 `127.0.0.1` 当成宿主机。

新部署先完成管理员初始化，再开放公共反向代理。远程服务器可从自己的电脑建立 SSH 隧道，将下列 SSH 目标替换为实际用户名和主机：

```sh
ssh -N -L 6240:127.0.0.1:6240 user@server
```

保持隧道连接，在本机打开 `http://localhost:6240` 创建管理员；如已修改宿主端口映射，相应调整隧道的远端端口。初始化成功、确认能登录后关闭隧道，再配置公开 HTTPS。首次初始化没有额外令牌，能够访问该页面的人就有机会创建管理员；Origin 校验不能代替这一访问范围限制。

默认根据浏览器 Origin 与请求 Host 校验来源，HTTPS 来源使用 `Secure` 会话 Cookie。反向代理必须保留公开域名和端口；应用不使用 `X-Forwarded-Host` 替代 Host。可选的 `APP_ORIGIN` 会进一步锁定完整访问源，配置后必须与实际访问地址一致。

VNC 与面板共用域名和端口，代理需支持 WebSocket Upgrade。以下设置可加入现有 Nginx/OpenResty 代理 location；它不是完整站点配置：

```nginx
proxy_http_version 1.1;
proxy_set_header Host $http_host;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
proxy_read_timeout 3600s;
proxy_send_timeout 3600s;
```

保留正确的 Host/Origin。不要另外公开 5900、6080 或绕过网关转发控制台。应用主机需要能以 SSH 协议连接 OCI 控制台服务的 TCP 443，仅支持 HTTPS 的出口代理不一定能承载该连接。

## 运行、停止与健康检查

```sh
docker compose ps app
docker compose logs --tail 100 app
docker compose exec app node dist/health.mjs
```

镜像使用 Tini 作为进程入口，处理信号转发与子进程回收；`node dist/runtime.mjs` 管理独立的 Web 和 Worker 进程，并提供 HTTP/WebSocket 网关。业务进程意外退出时，运行入口停止另一个进程并非零退出，交由 Compose 中的 `restart: unless-stopped` 重启容器。

整体健康检查同时验证 Web、SQLite 和当前 Worker 心跳；`GET /api/health` 只检查 Web 与 SQLite。Docker 的 `unhealthy` 标记本身不会触发 Compose 重启策略。

```sh
docker compose stop app
docker compose up -d app
```

优先等待活动任务和控制台会话结束后停止。Worker、运行入口和 Compose 的停止期限分别为 25、30、35 秒。停止进程不会撤销 OCI 已受理的操作；手动停止后的容器不会自行重启。

数据卷或宿主目录应位于支持本地文件锁的文件系统。本部署不支持多主机通过 NFS 共享 SQLite。普通 `docker compose down` 保留命名卷；`down -v` 会删除声明的命名卷，不用于日常重启。

## 账号、同步与任务

账号卡片的“详情”打开时按需调用 OCI 的 `getTenancy`、`getUser` 和 `listRegionSubscriptions`，不执行云资源变更。详情信息的读取权限与资源同步权限分别检查；其中一项失败不会使其他项消失，也不会自动修改账号连接状态。弹窗中的“刷新详情”重新读取这些信息，不会启动资源同步。

配置主区域与 OCI 实际主区域分别展示。资源概况来自当前配置区域的已同步库存，不包含未同步区域、已移除实例或未关联的磁盘，也不是免费额度或资源配额；缺失的 OCPU、内存和启动卷容量不补为零。

同一租户保存一份配置。更新 API 密钥或增减区域时编辑已有账号；新增或更换租户时会拒绝重复配置。资源归属冲突需要先在设置中处理。

首次连接、凭据变化、错误重连、名称待识别或没有同步记录时，Worker 先验证账号；正常已连接账号直接读取库存。可见资源页每 60 秒检查账号是否过期，同一账号的活动同步合并，失败逐步退避到最多 15 分钟。

手动刷新按各账号完成情况逐步读取快照。页面隐藏、离开或等待超时只停止浏览器轮询，后台任务继续。自动同步不进入普通任务列表；每个账号只保留最近的已结束自动记录，手动任务保留历史。

| 状态                                 | 运维含义                                                                     |
| ------------------------------------ | ---------------------------------------------------------------------------- |
| `queued` / `running`                 | 已排队，或由 Worker 持有租约执行。                                           |
| `retrying`                           | 可重试错误，等待下次执行。                                                   |
| `cancel_requested`                   | 等待安全边界停止；不回滚已接受的云操作。                                     |
| `interrupted`                        | 执行器退出或租约失效，需要核对检查点；有剩余预算和下次执行时间时可自动恢复。 |
| `succeeded` / `failed` / `cancelled` | 已结束；失败或取消不代表云端从未发生变化。                                   |

请求错误默认最多尝试 4 次。OCI 已受理但尚未完成时，核对结果不消耗错误重试次数；每轮执行有自首次领取起的 30 分钟完成期限，重启不会延长期限。手动重试保留任务编号和检查点，增加预算并开启新的完成期限。

同一 Worker 最多同时同步两个账号并执行一个写任务。SQLite 约束写任务全局串行，以及同账号同步与写入互斥。写操作成功但随后库存刷新失败时会另排同步任务，不应为刷新页面而重复执行写操作。

在实例卡片、表格或网络页点击 IP，可打开统一地址详情。固定或受保护地址、私网 IPv4、IPv6、信息不完整、实例状态不支持或任务未结束时，更换按钮保持禁用，弹窗说明原因。可更换的临时公网 IPv4 在同一弹窗内确认提交，旧地址释放后无法保证找回。弹窗打开后绑定发生变化时，应关闭并重新打开当前地址；查看详情和复制不会提交更换任务。

## VNC 控制台

需要 OCI 实例读取和控制台连接创建、列举、读取、删除权限。应用使用临时 SSH 密钥，不要求实例 SSH 服务或公网 IP 可用，也不会安装来宾 VNC 服务。

全站同时一个会话，15 分钟无操作或达到 1 小时上限后断开。关闭页面、登出或服务重启会触发清理。应用仅删除与记录中的账号、实例和会话标签匹配的连接，已有外部控制台不会被删除。

SSH 外层服务密钥须匹配 OCI API 指纹；内层仅通过该认证通道记录本次主机密钥。镜像设置 `TMPDIR=/dev/shm`，使用 Docker 默认私有 tmpfs（默认 64 MiB）保存 SSH 临时文件和运行状态；正常断开删除临时密钥，停止容器后内存文件系统不保留。无需额外挂载 `/tmp`。

清理失败时保留全局会话占用和账号锁，并定时重试。404 仍需通过所属实例的连接列表确认消失；权限不足或创建结果不明时不能释放占用。先恢复 OCI 权限，再使用“重试断开”；不要通过删除数据库行绕过清理。

### 旧 API 密钥已失效时

如果清理因 API 密钥撤销而一直失败，可受控替换清理凭据：

1. 先断开控制台，等待已经发出的创建、清理请求真正结束，并结束或取消该账号未完成的任务。
2. 在“设置 → OCI 账号”编辑该账号，选择“替换连接凭据”和“恢复控制台清理（旧 API 密钥已失效）”。
3. 提供**同一 tenancy、同一 user** 的新 OCI API 配置及对应 RSA PEM。原 home region 和同步区域保持不变。
4. 保存后等待后台以新凭据重试清理。全局占用仍保留，清理成功后再手动连接和同步资源。

只有失败、待清理、本机隧道已关闭、没有在途创建/清理且账号没有未结束任务的会话接受该操作；不满足条件时会拒绝保存。此恢复不会自动排队同步，也不允许更换账号身份或区域。

会话持久化已验证的所属区间，清理不依赖实例仍然存在；权限不足或无法确认连接已经删除时，继续保留清理锁。

## 备份

备份至少包括 `/data` 对应的完整命名卷或宿主目录、匹配版本的镜像或可重建源码，以及管理员恢复材料。持久数据包含 `.master-key`，应把归档视为可解密的敏感数据；加密存储不保护整个目录或卷泄露、主机失陷。数据库里的资源名称、IP、任务和统计报告不是全库加密。

只下载发布 Compose 的用户可以使用自己的 Docker 卷备份或宿主目录归档工具，不需要 Node.js。先结束活动任务和控制台会话，记录原运行状态，再执行 `docker compose stop app` 并确认已停止。完整归档挂载到 `/data` 的目录内容，包括数据库、WAL 等配套文件和隐藏的 `.master-key`；保留所有者和权限。备份目标必须在源数据目录之外，同时保存对应版本的 Compose 及自己的可选配置。备份完成后，仅在原来运行时恢复 `docker compose start app`。

源码仓库另提供自动处理停止、归档及原状态恢复的工具；它不包含在单份发布 Compose 中，也不是普通部署的前置条件。额外取得对应版本源码、Node.js `26.13.0` 和 Docker CLI 后，可显式选择已有部署执行，例如：

```sh
COMPOSE_FILE=/opt/oci-dash/compose.yaml \
COMPOSE_PROJECT_NAME=oci-dash \
node /opt/oci-dash-source/scripts/backup.ts /opt/backups/oci-dash-data.tar.gz
```

将示例路径和项目名替换为实际部署；已有自定义项目名必须保留，不能指向开发项目。工具不需要重新构建或启动新镜像，也可在源码目录通过 `npm run backup -- <输出路径>` 调用，但仍须正确选择部署的 `COMPOSE_FILE`、`COMPOSE_PROJECT_NAME`。它读取现有 `app` 容器的不可变镜像，支持 `/data` 的命名卷和宿主目录；自定义容器内数据库路径不在此工具范围内。输出必须是项目及源数据目录之外、以 `.tar.gz` 结尾的新文件，不覆盖已有归档。

脚本停止应用后，以 root 运行临时归档容器，只读挂载原数据。归档通过标准输出传给宿主进程写入，数据源的属主和权限保持不变。备份前应用正在运行才会在结束后恢复运行，原本停止的应用保持停止。

使用仅自己可访问的目标目录。Unix 上归档应为 `0600`；Windows 还需使用目录 ACL 限制访问。如果备份或恢复运行状态失败，应按错误信息检查容器状态，不要把失败过程当作成功备份。

归档不替你备份可选的外部配置。不要通过日志、聊天、Issue 或截图传递密钥。不要只复制运行中的 `.db` 而遗漏 WAL 和密钥，也不要把数据库归档存回仓库。

## 恢复与升级

恢复先在隔离环境演练：

1. 准备与备份匹配的镜像，以及包含原 `.master-key` 的完整归档。恢复的是该版本的数据，不进行数据库格式转换。
2. 把 Compose 放入独立恢复目录，使用新的项目名、该目录内空的 `data` 和不同宿主机端口；如配置了 `APP_ORIGIN`，同步调整。核对解析后的挂载实际指向恢复目录；只更改项目名不会隔离宿主目录，不能沿用生产路径。
3. 将归档完整恢复到该项目的 `/data` 挂载，保留所有者和权限，确保挂载可读写。保留生产数据不动。
4. 在启动 Worker 前核对数据库完整性、管理员登录、账号和非终态任务。

默认入口会启动 Worker，可能继续恢复的任务。只检查 Web 时，可在隔离项目中临时覆盖命令，并选择一个未使用的 loopback 端口（示例为 3001）：

```sh
docker compose -p oci-dash-restore run --publish 127.0.0.1:3001:3000 \
  --rm --no-deps app node server.js
```

该命令不启动 Worker 或 VNC 网关，但 Web API 仍能接收操作请求，并非只读模式。缺少 Worker 心跳时整体健康检查失败是预期现象；可用 HTTP `/api/health` 检查 Web/SQLite。结束检查后停止该临时容器。

备份可能早于云操作实际完成时间。核对 OCI 状态、任务检查点和请求标识后，才在对应隔离项目启动完整应用。恢复本地数据不是云资源回滚。完整异机恢复演练的验证状态见[验证指南](VERIFICATION.md)。

更新前完成一致性备份并保留匹配的镜像。先核对目标版本的数据库要求：本版从独立空 `data` 初始化，不提供接入 Drizzle 之前数据库的自动升级；原数据与原版本环境另行保留。

对于目标版本明确支持的数据格式，使用仓库默认 Compose 时执行下面的命令更新 `latest`；运行中的容器不会自动更新。需要固定版本时，从目标版本的 GitHub Release 下载对应 `compose.yaml`。保留项目名、服务名 `app`、实际数据目录、端口映射和必要的高级覆盖配置：

```sh
docker compose pull app
docker compose up -d --wait app
docker compose exec app node dist/health.mjs
```

数据库初始化和已提交迁移由启动流程执行，没有通用降级转换。回退使用互相匹配的镜像和备份，不把任意版本直接指向其他版本的数据。直接更换 `MASTER_KEY` 也不是密钥轮换。

## 常见问题

| 现象                       | 优先检查                                                                                             |
| -------------------------- | ---------------------------------------------------------------------------------------------------- |
| 页面正常，任务不执行       | 整体健康检查、Worker 日志、任务状态、租约和重试时间。                                                |
| 登录或写请求来源不匹配     | 浏览器 Origin 与代理保留的 Host 是否一致，以及可选 `APP_ORIGIN` 限制。                               |
| 导入或恢复后无法解密       | 数据库与原 `.master-key` 是否配套；恢复归档是否完整。                                                |
| 修改初始化密码后仍无法登录 | 初始化变量不会重置已有管理员；默认 Compose 不注入 `.env` 中的应用变量，正常改密在“设置 → 登录安全”。 |
| 恢复后出现初始化或空面板   | 先停止应用，核对 Compose 所在目录、实际挂载、数据版本及完整性，不要创建替代管理员。                  |
| 数据目录无法启动           | `/data` 实际挂载是否可读写、磁盘空间和宿主文件系统限制；Docker Desktop 是否允许宿主目录访问。        |
| 部分库存未更新             | 同步 warnings、OCI 权限与可见区间；旧详情会保留并标记。                                              |
| 指标或费用缺失             | Monitoring/Usage API 权限、时间范围和采集代理；详见[统计说明](ANALYTICS.md)。                        |
| 任务结果不确定             | 先核对远端状态和检查点，再决定重试或取消。                                                           |

当前没有忘记管理员密码后的自动找回工具，也没有批量主密钥重加密工具。请在需要恢复前保存管理员恢复码、主密钥和一致性备份。
